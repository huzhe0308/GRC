# GB/T 45181-2024 车联网网络安全异常行为检测机制

## Overview

GB/T 45181-2024 specifies a security-related misbehavior detection mechanism for connected vehicles (车联网网络安全异常行为检测机制). Identical to ITU-T X.1376:2021, it defines a big-data-based detection mechanism for cybersecurity anomalies in connected vehicle environments. The standard covers the complete detection pipeline from data collection through detection engine operation and optimization, with informative appendices providing concrete use cases for four distinct detection methods. It is essential for connected vehicle security architects designing intrusion and anomaly detection systems that process heterogeneous vehicle data streams.

## Scope and Requirements

- **Scope**: Provides a recommended mechanism for detecting cybersecurity misbehavior/anomalies in connected vehicles, covering data collection, detection, and optimization. Data acquisition methods and notification module usage are out of scope.
- **Detection Mechanism Model** (§6): Defines overall architecture with two systems — data collection (data acquisition, filtering, cleaning) and detection (data selection, detection engine, optimization).
- **Data Collection** (§7): Specifies three data types:
  - **State data** (状态数据): Application/service data, vehicle state (safety systems like ABS, airbags, AEB, ADAS; body systems; chassis; powertrain), environmental sensors (radar, LiDAR, ultrasonic, camera, ITS sensors)
  - **Control data** (控制数据): Local control (in-vehicle controllers) and remote control (automation, telematics, remote diagnostics)
  - **Intelligence data** (情报数据): Internal (vulnerabilities, defects, security incidents) and external shared (IP addresses, hashes, URLs, domains, CVEs)
- **Detection Engine** (§8.2): Comprises detection methods and decision sub-modules. Four detection methods defined:
  - **State chain detection** (§8.2.1.1): Single-chain and branch modes for correlated state data; detects anomalies by comparing node context and value trends
  - **Control flow detection** (§8.2.1.2): Single-chain and branch modes for control data; detects unauthorized control paths (e.g., MCU called without API service log)
  - **Time series detection** (§8.2.1.3): Analyzes trend, periodicity, randomness, and superposition patterns in time-sequenced data (e.g., CAN messages, GNSS position reports)
  - **Correlation intelligence detection** (§8.2.1.4): Direct (IP/domain/CVE) and indirect (combined with other data to detect attack chains)
- **Decision Module** (§8.2.2): Three outcomes — anomalous, suspicious, or normal. Uses scoring against stable baseline; human analyst介入 for suspicious cases.
- **Optimization** (§8.3): Feedback module that improves detection engine, data selection, and data collection based on detection results.
- **Editorial Changes from ITU-T**: Renamed to 车联网网络安全异常行为检测机制; added connecting lines/graphics to figures 4-8; changed letter annotations to notes.

## Technical Details

- **Use Case A.1 (State Chain)**: TCU low-power mode state mismatch between vehicle gateway and TU state cache detects cyber anomaly — if states differ, vehicle cannot be in low-power mode while driving.
- **Use Case A.2 (Control Flow)**: Remote vehicle control generates operation logs at mobile app, API service access logs, TCU call logs, and actuator logs. Absence of logs at any node indicates anomalous path.
- **Use Case A.3 (Time Series)**: GNSS spoofing detected by latitude/time-interval deviation from established pattern (e.g., 39.95° latitude with 10s intervals shifting to 45.95° latitude with 5s intervals).
- **Use Case A.4 (Correlation Intelligence)**: Direct — IP/domain/CVE matches in intelligence database. Indirect — combining browser version with CVE-2017-11906/11907 reports to detect exploitable attack chains.
- **Abbreviations**: ABS, ADAS, AEB, API, CAN, CVE, GNSS, IP, ITS, LiDAR, MCU, OEM, TCU, URL.
