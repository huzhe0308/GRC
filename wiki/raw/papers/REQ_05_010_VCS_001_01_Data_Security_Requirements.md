# REQ_05_010_VCS_001_01_Data_Security_Requirements


整车数据安全需求 Data Security Requirements


1. 文档概述


1.1. 产品目标


打造清晰、合规、高效的车机系统个人信息保护流程和机制，保障用户数据安全与知情权，提升用户对车机系统的信任度，让整车契合行业数据安全法规要求。


本文档定义了和数据安全相关的个人信息保护的产品需求，包括针对一般个人信息所需的隐私协议、针对敏感个人信息的单独授权同意的设计指导文档，适用于CEA2.X平台车型。

1.4. 行业情况分析


1.4.1. 行业现状


一、合规要求趋严


随着《汽车数据安全管理若干规定》、《个人信息保护法》等法规的落地，车机系统座位汽车数据核心交互 载体，隐私与权限管理合规性成为产品准入关键门槛，违规案例的曝光倒逼企业强化授权流程的合规化设 计。


二、用户体验待优化


当前多数车机授权流程存在“重合规、轻体验”问题，权限说明晦涩、流程繁琐、开关重复，导致用户授 权转化率低，部分用户因嫌麻烦放弃使用该功能，同时授权后因隐私顾虑频繁投诉，影响产品口碑。


三、功能与数据深度融合趋势


智能驾驶、智能座舱功能迭代，车机需调用更多敏感数据（如人脸信息、声纹信息、高精地图），权限类型 复杂程度提升，如何在保障功能体验的同时，平衡数据安全与用户授权体验，成为行业共性挑战。


1.4.2. 产品借鉴


一、特斯拉


设计逻辑：在系统设置中提供独立的总开关，一键控制某类权限的全局开启/关闭，同时支持对具体功能的 细分控制。


产品流程：车机系统「安全与隐私」设置中，设有 、独立总开关，关闭后所有依赖该 权限的功能（如哨兵模式、语音助手）均无法调用。同时，GPS 定位权限需在导航设置中单独管理，支持 全局关闭或仅允许特定应用使用。


二、宝马 iDrive 系统


设计逻辑：不设置全局总开关，用户需在具体功能中单独管理权限，更强调场景化授权。


产品流程：未提供麦克风、摄像头的全局总开关，用户需在中开启麦克风权限，在 中开启摄像头权限，GPS 定位则在导航应用内单独设置。


三、理想 L 系列车机


设计逻辑：既有全局总开关，也支持对细分功能的独立控制，平衡隐私保护与功能灵活性。


产品流程：在 - 中设有 、，关闭后所有相关功能禁用；同 时，GPS 定位支持在中全局关闭，或在中单独允许辅助驾驶使用位置信息（如关 闭导航时的 GPS，但保留自适应巡航的定位功能）。


1.5. 产品策略


本功能的产品定位是基于法规要求，为大众车主提供清晰、友好的隐私数据授权流程。


授权清晰易懂


交互设计上采用“父类目+功能级权限开关”的模式，既满足用户对隐私的快速管理需求，又能使用户可以 精细化管理各系统功能的敏感信息权限，既能提升用户对隐私的掌控感，又能确保车机功能的正常使用， 符合当前智能汽车隐私保护的行业趋势。


合规保障策略


产品设计时充分考虑相关实体法规团队的意见，梳理隐私数据条款和系统权限的授权流程，确保授权流程 与最新法规适配，保障全环节合规。


授权管理从通用隐私数据授权到敏感隐私信息开关授权，在授权流程中通过用户主动勾选、可选择的带期 限同意，增强用户对大众车机系统的合规感知。

2. 需求详细设计


2.1. 一般个人信息保护


2.1.1. 功能概述


构建清晰、合规、易读的个人信息保护流程，明确车机系统数据采集、使用、存储、共享规则，保障 用户知情权与选择权，满足行业法规（如《个人信息保护法》、《汽车数据安全管理若干规定》及GB/T44464第5章个人信息保护要求。


2.1.2. 需求详情


2.1.2.1. 个人同意


汽车数据处理者处理个人信息应取得个人同意，需通过至少一种显著方式向个人告知，清晰地说明处理个人信息的具体情境和必要性。


功能描述：


对于涉及一般个人信息的功能，需要有至少一种显著方式向个人告知，不限于单独的隐私协议，或将事实输入加入到整车通用隐私协议中等


告知内容应至少包含：


处理个人信息的种类，处理各类个人信息的必要性，处理目的、方式、用途等；


收集各类个人信息的具体情境以及停止收集的方式和情境；


个人信息存储地点、存储期限，或者确定存储地点、存储期限的规则；


查阅、复制其个人信息以及删除车内、请求删除已经提供给车外的个人信息的方式和


途径；


用户权益事务联系人的姓名和联系方式；


法律、行政法规规定的应告知的其他事项


取得个人同意的选项设置


汽车数据处理者应按以下要求设置取得个人同意的选项：


提供同意和拒绝的方式；


重新取得个人同意


当个人信息的处理目的，处理方式和处理个人信息种类发生变更时，汽车数据处理者应重新取得个人同意


例：隐私协议中若涉及某功能的事实输入（个人信息相关）发生变更时，要触发隐私协议的重新弹窗同意逻辑


个人同意的撤回


汽车数据处理者应提供撤回个人同意的途径


例：车机恢复出厂设置后用户需重新同意通用隐私协议


2.2. 敏感个人信息保护


2.2.1. 功能概述


构建清晰、合规、易读的个人信息保护流程，明确车机系统数据采集、使用、存储、共享规则，保障 用户知情权与选择权，满足行业法规（如《个人信息保护法》、《汽车数据安全管理若干规定》及GB/T44464第5章个人信息保护要求。


2.2.2. 需求详情


2.2.2.1. 个人同意


汽车数据处理者处理敏感个人信息应取得个人同意，需通过至少一种显著方式向个人告知，清晰地说明处理个人信息的具体情境和必要性。


功能描述：


对于涉及敏感个人信息的功能，需要有至少一种显著方式向个人告知，单独授权用户并征得用户同意


告知内容应至少包含：


处理个人信息的种类，处理各类个人信息的必要性，处理目的、方式、用途等；


收集各类个人信息的具体情境以及停止收集的方式和情境；


个人信息存储地点、存储期限，或者确定存储地点、存储期限的规则；


查阅、复制其个人信息以及删除车内、请求删除已经提供给车外的个人信息的方式和


途径；


用户权益事务联系人的姓名和联系方式；


法律、行政法规规定的应告知的其他事项


取得个人同意的选项设置汽车数据处理者应按以下要求设置取得个人同意的选项：提供同意和拒绝的方式；


提供自主设定处理敏感个人信息同意期限的途径，且期限不应设置为始终允许或永久。


例：


重新取得个人同意

应重新取得个人同意；


例：某涉及麦克风权限的功能的收集音频信息的处理目的发生变更时，要触发单独授

汽车数据处理者应提供撤回个人同意的途径


例：通过车机设置中关闭车机使用麦克风权限后，和麦克风相关的功能无法收集车内


音频信息（声纹信息）


2.3.数据匿名化2.3.1数据匿名化定义1. 识别视频或图像中的人脸或车牌区域，并擦除特定信息；2. 擦除区域与实际面部或车牌区域的交点应为已配置；3. 建议在脱敏区域涂上均匀的色块；4. 应确保无法使用任何图像恢复技术进行恢复脱敏区域。


2.3.2 车牌要求应使用以下车牌类型：


大型汽车牌照、普通摩托车牌照、拖车牌照、小型汽车牌照、新能源汽车专用牌照、大使馆和领事馆汽车号牌、香港、澳门出入境车辆号牌牌照、教练牌照、警车牌照、消防救援车牌照、香港车辆牌照和澳门车辆牌照。


（见附件1）港澳车牌示意)


在不限制车牌数量的情况下，对多个车牌进行脱敏处理应支持单个图像。


视频中静止、朝同一方向行驶的车牌脱敏，应支持反向行驶等。


2.3.3 人脸要求不同年龄段（老年人、青年和中年人、儿童）、不同性别和应采用不同种族（黄色、白色和其他有色人种）。


应支持识别远近不同距离的人脸。（最小像素面积见GBT44464）


应支撑多角度面。


对多张人脸进行脱敏处理，不限制单张图像中的人脸数量得到支持。


视频中静止、行走、跑步、骑行等肖像的脱敏处理应支持。


在戴口罩、眼镜、耳机、耳环、帽子等条件下面部脱敏。


2.3.4 性能要求应考虑正确处理特殊情况，例如基于人工智能的算法生成的人脸和车牌。


应满足检测率和误检率：


|   | 检测率 | 误检率 |
| 人脸 | 90% | 10% |
| 车牌 | 90% | 10% |


2.3.5 场景鲁棒性要求（Nice To Have）1. 应支持公路、城市道路、交通圈、地面和地下停车场场景；


2. 应支持日间和夜间照明环境；


3. 应支持晴天和雨天的可见场景。
