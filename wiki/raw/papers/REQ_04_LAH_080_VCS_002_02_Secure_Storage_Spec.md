1.3 目的
本规范描述了对于安全存储涉及的，如密钥和数据的安全需求，并提出了相应的控制措施。针
对安全存储保护的数据及类型，从数据的真实性和/或机密性上提出对应的安全需求，并引出适
用的安全控制措施。
1.3.1 安全存储功能概述
为了防止存储在本地的，需要保护的数据、密钥等被泄露和篡改，这些数据应被保存在受保护
的存储空间，例如 MCU 的内部安全存储器，硬件安全模块（ HSM ），或外部存储器
（EEPROM，FLASH 等）但用密码学算法进行保护的区域。
同时，用来对这些数据（包括密钥）进行密码学算法保护的密钥，也需存储在受保护的存储空
间，密码学运算应在安全执行环境中执行，进行机密性和/或完整性保护。
1.3.2 范围
1.3.2.1 密钥的安全存储
密钥的种类：对称密钥，非对称密钥的私钥。
关键密钥需存储在硬件支持的安全存储区域内，如 HSM 等使用类似技术保护的安全区域。
密钥需实施机密性和完整性保护。
1.3.2.2 数据的安全存储
数据存储部分主要包含各类存储器上的需要机密性或真实性保护的材料和其他安全相关状态标
志。
数据安全存储需考虑数据的机密性和/或真实性。

2. 文档交付要求
ECU 的供应商必须向客户提供安全存储方案文档，描述哪些数据应受到安全存储的保护，
并详细说明了如何满足本文档中的每个要求。
ECU 的供应商必须记录每个 MCU/SoC，使用哪些方法来确定受安全存储保护的数据的真实
性，完整性和机密性。
ECU 的供应商必须向 OEM 提供针对安全存储方案的测试报告，以及安全模块（如 HSM，
TEE 等）的性能指标测试数据。
所有与本文件和所有进一步适用文件（参见第 1.2 章）的要求相悖的行为必须由供应商记录并
得到客户的批准。
3. 技术要求
3.1 基本需求
需进行安全存储的数据，应储存在受基于硬件的安全措施保护的安全存储空间，或存储在受
密码学算法保护的安全存储空间。
用于实现安全存储的密钥，应存储在受基于硬件的安全措施保护的存储空间。
应使用合适的安全隔离技术保护安全存储区域，并限制对安全存储区域的访问。
可使用硬件安全隔离技术（如安全的总线架构）或支持安全隔离的方案（如 HSM，TEE 等）
执行安全存储区域的隔离。
应对访问安全存储空间的主体执行身份认证保护，防止非授权访问。
可使用密码学算法（如消息验证码 MAC）的方式对访问主体进行身份认证。
应在系统上使用访问控制措施执行对受保护数据的访问控制。
可使用强制访问控制（MAC）或基于角色的访问控制（RBAC）执行访问控制。
注意：安全存储机制并不能防止数据被获得授权的用户来调用。它只能保护数据不被另外的系
统或直接对存储空间的非法数据调用。
应使用OTP 方式等一次性编程区域，实现设备唯一密钥和唯一识别码的写入。
如果数据从一个设备克隆到另一个设备，由于每个设备上的密钥都是唯一的，对应的加密
密钥也会不一致，从而达到数据的防克隆。

安全存储必须绑定到特定设备，这意味着数据被创建时，只有在同一执行环境和同一设备上认
证的授权主体才能访问或修改。
应使用MAC（消息验证码）或数字签名的方式对存储数据实施真实性和完整性保护。
应使用加密的方式对需要机密性保护的数据实施加密保护，并符合相应密码算法安全要求。
应使用单调计数器或随机数的方式防止对安全存储对象的重放攻击或数据回滚攻击。
对于需要删除的数据（比如隐私数据、密钥等），应保证数据被删除后不能恢复。
可以使用以下两种方法删除敏感数据：
1. 用一个固定的值来覆写每个字节，比如归零；
2. 通过删除加密密钥来使得所有被加密的数据无法再被解密(密码删除)。
应支持硬件唯一密钥（HUK），保证每个设备上的 HUK 都是唯一的，并对 HUK 的访问做限制;
HUK 可用作主密钥（Master key）或根密钥（Root key ）。
应支持通过主密钥衍生相应的安全存储密钥；
注意：这一机制的核心是通过使用一系列密钥衍生步骤来确保上游密钥（root key 或者
master key）的安全性，同时允许下游密钥（derived keys）在不暴露上游密钥的情况下用于
各种操作。
应保证只有认证授权的主体（用户，进程）才能使用该主体所拥有的密钥。
对于用于实现安全存储的密钥，应根据密钥的不同用途，支持对密钥属性的配置。
密钥的用途必须在属性规定的范围内使用（如，加密存储密钥只能用来加解密，消息校验密钥
只能来做 MAC，身份认证密钥只能用来做验签，身份认证私钥应不支持导出）。
3.2 安全存储实现的要求
通过使用的芯片提供安全环境，以及为需要机密性保护的数据（如加密密钥）提供受保护的存
储空间。可以防止未经授权的泄露，包括克隆和受保护的数据存储如根证书防止非授权的修改。
本规范提出了针对HSM，TEE, e.MMC和外部Flash的安全存储要求，实际实现可以是其中的一种
或他们的结合。

3.2.1 HSM
HSM 内部的加密密钥材料应被安全地存储在其安全存储区域中。
密钥存储应利用硬件提供的屏蔽机制，并额外使用硬件内部的 ROM 密钥对所有材料进行加密，
作为额外的安全层。
即使攻击者成功读取了 HSM 数据闪存内容，只要 ROM 密钥保持秘密，密钥仍然是安全的。
应使用密钥属性限制密钥用途，使其仅用于特定的安全用例。
例如，属性"仅验证"将密钥限制为仅用于验证 MAC 而不是生成 MAC。
密钥属性应在首次提供给 HSM 的内部安全密钥存储时与加密密钥紧密关联存储。
密钥属性应被静态地分配给一个密钥存储槽，并且与正在使用的变体有关。
应通过专用的软件接口调用存储在 HSM DFlash 中安全数据。安全数据以应经过身份验证和
加密的形式存储。
安全数据是指通过直接内存读取操作无法从主机访问的持久存储数据。
身份验证和加密是块特定和设备特定的（即，即使包含相同用户数据的两个不同块在 DFlash
中也产生不同的加密数据，并且在另一台设备上也产生不同的加密数据）。因此，从一个 ECU
的 DFlash 转储不能用于另一个 ECU。
与安全密钥存储类似，数据存储也是可定制的。可用块的数量和块大小可进行配置。 在每个
预配置的块内，用户可以存储任何数据。
3.2.2 TEE
存储在富执行环境 （REE）的密钥材料应使用消息验证码（MAC）的机制保护密钥的完整性
和真实性。
存储在 REE 的对称密钥和非对称私钥应使用加密的措施保护。
用来生成安全保护（加密或 MAC 计算）的密钥应存储在OTP/e-Fuse，并且只能在安全环境下访
问。
可信存储（Trusted storage）可以由非安全资源实现，只要应用适当的密码学保护措施，密码
学措施的强度应该至少和 TEE 的代码和数据具有相同强度。
可信存储（Trusted storage）必须只允许被授权的 TA 访问和修改。
可信应用（TA）应有能力隐藏用于加密数据的秘钥材料。
每个 TA 都应有能力访问自己的存储空间，同时也能满足隔绝于其他 TA 的访问的需求。

3.2.3 e.MMC
应使用 RPMB 技术保护 e.MMC 上存储的安全数据。
RPMB 密钥应与 CPU ID 关联。
这意味着，更换 CPU 应一同更换 eMMC。
对于需要机密性保护的数据，存储到 RPMB 分区时应进行加密后再存储。
RPMB 可以对写入操作进行鉴权，但是读取并不需要鉴权，任何人都可以进行读取的操作。
RPMB 使用对称密钥进行认证，因此必须在主机和存储设备上使用相同的认证密钥（也成为
“共享密钥”或 RPMB 密钥）。
使用 e.MMC 的作为安全存储时，应为每一个 e.MMC 生成一个唯一的 256 bits 的安全密钥
（RPMB Secure Key），在安全环境中（如产线）通过主机写入到 e.MMC 的 OTP 区域（只
能烧写一次的区域），同时 Host 在安全区域中（例如：TEE）也保留相同的 Secure Key。
在进行读取操作时，应避免使用相同的随机数生成器或不安全的随机数生成器来生成 nonce，
以防止数据重放用于读取访问。
3.2.4 外部存储模块
应保护数据免受未经授权的操纵。
应针对数据的机密性和真实性的保护要求选取加密算法。
ECU上安全存储的需求由网络信息安全架构指导，若ECU属于可以接受不使用硬件安全存储
环境的等级，可以通过将密钥混淆落盘在外部存储模块并采取安全访问防护机制安全存储密
钥，需由相应安全机制的负责人和安全存储，以及涉及该密钥相关功能的负责人审批同意。

4.2 基于 TEE 的安全存储
当 TA 调用 GP 可信存储 API 提供的写函数将数据写入持久对象时，将调用 TEE 可信存储服
务中实现的相应系统调用，该系统调用一系列 TEE 文件操作来存储数据。TEE 文件系统将对
数据进行加密，并通过一系列 RPC 消息向 TEE 请求者发送 REE 文件操作命令和加密数据。
TEE 请求者将接收消息并将加密的数据相应地存储到 Linux 文件系统。读取文件的处理方式
类似。详细流程参考GP 规范[4]。
4.3 基于e.MMC 的安全存储
重放保护的基本思想是确保每条消息都是唯一的。在 RPMB 中，设备管理一个只读计数
器，该计数器在每条写入消息后递增，其新值将为包括在下一个要发送的验证码的计算
中。
RPMB 命令通过 HMAC SHA-256 计算进行身份验证，该计算作为输入：
￮
共享/密钥。
￮
包含写入命令或读取结果的消息。
￮
写入计数器，它计算对 RPMB 的写入总数。
￮
随机数，是每个读取命令的随机生成的数字。
生成的MAC 是一个 256 位（32 字节）密码，嵌入在 RPMB 数据帧中，并随消息数据本
身。

4.4 基于外部存储的密码学保护示例
4.4.1 外部存储安全存储数据示例（供参考）
每次加密数据时，应使用不同的初始化向量（I V ）。避免加密相同数据时，从密文发现明文的
规律。应对存储的数据 加密并按照安全存储的布局进行存储。
当存储数据时，GCM 标签，IV 也应被存储。对于 AES-GCM 模式，唯一 ID（Unique ID， 不
同于 IV）也作为真实性标签的一部分，用作“additional authenticated data (AAD)” 数据应作为
AES-GCM 的输入。
存储的数据布局如下：
AAD + 96bit + IV + 128bit GCM Tag + Data
应使用不同的安全存储密钥对属于不同主体的存储数据对象做保护，以避免一个主体拥有的数
据可能被用来在另一个主体上解密；
当解密数据时，GCM 标签需要再次计算，并与参考值进行比较，比较一致后，存储的数据才
能被使用。
当解密出错时，应立即停止，并报错，记录相应日志。
4.4.2 外部存储安全存储安全日志的示例（供参考）
应使用对称或非对称的加密方式来确保日志存储的完整性和真实性，为此，将计算参考值（即
对称 MAC 或数字签名）。
对于用加密确保机密性，通常使用对称算法，同时应使用“认证加密”算法确保一次操作的加密
和真实性。

1.2 定义
供应商以及供应商的转包商都被定义为“供应商”。
供应商的承包商被定义为“OEM”。
本文档中的关键词“必须”、“不得”、“必需”、“应”、“不应”、“应该”、“不建议”、“建议”、“可以”
和 “可选”应按照 RFC2119 [1] 中的描述进行解释。
关键词依次对应的英文为：
“MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”,
“RECOMMENDED”, “MAY”, and “OPTIONAL” 。
1.3 目的
本文档描述了使用所谓的硬件安全执行环境（HSEE）所需的硬件和软件的要求，这些硬件和
软件用于在控制单元中网络安全功能。
HSEE 需要 CPU 的封装执行环境，通过额外的硬件支持的保护性措施（如物理上分离的存储和
计算单元）来防止未经授权的访问和影响。保护性措施不仅必须类似于内部存储器对CPU 外
部实的体起作用，而且还必须对同一 CPU 内的其它部分（“主 CPU”）未授权的访问起作用。
HSEE 包括设计为 HSM 的CPU 的单独专用内核，以及其它相应的 CPU 的保护环境，如 ARM
TrustZone。
为了使 HSEE 履行其功能，它只能执行与安全范围相关的功能，从而最大限度的减少潜在的攻
击面。
HSEE 必须以这样一种方式保留敏感数据，即主机 CPU 的完整性在运行时丢失，数据的机密性
和真实性也会得到保证。此外，HSEE 可以有额外的保护措施，让通过硬件攻击的方式读取或
操作保存在内部存储的数据变得困难。
此外，文档中包含了软件设计和安全机制实施的通用要求。

3 通用需求
在提交报价之前，必须与客户商定项目中使用的 HSEE 硬件。
3.1 实施问题
HSEE 的实现需确保，即使主机 CPU 的完整性在运行时丢失，数据的机密性和真实性也会得到
保证；同时，让通过硬件攻击的方式读取或操纵保存在内部存储的数据变得困难。
3.2 集成和集成审查
特定于项目的集成必须在项目开始商定的硬件上执行。
在 HSEE 全新开发的情况下，供应商必须实施测试，以识别安全漏洞（例如，通过渗透测试）
并向 OEM 分发结果文件。
3.3 测试
供应商必须提供执行的测试用例清单证据，并在必要时将这些测试结果提供给 OEM。
3.4 真随机数生成器（TRNG）
目标 ECU（需符合本文档规范的 ECU）应提供真随机数生成器（True Random Number
Generator）。真随机数生成器是 SoC/uC 的一部分。应使用多种熵源，其使用的熵源应该明
确。
HSEE 硬件必须有一个 AIS 31 P2 级别的真随机数生成器。
TRNG可作为专用IP模块独立实现，或作为SoC信任锚的核心组件。其熵源必须源于物理不可预测
现象，主要包括：半导体器件噪声（如二极管雪崩噪声、忆阻器电流波动）、模拟信号量化结果
（如温度传感器电压漂移）、时钟时序抖动。禁止使用软件可修改的数据（如系统时间、通用I/O）
作为熵源。信任锚集成时需具备物理防篡改设计和运行时自检能力。

HSM 硬件的性能应大于 1000DMIPS（大概一个现代 32 位 uC 在 500MHZ 的性能）
HSM 硬件应有自己的不小于 256KB 的 SRAM 区域.
HSM 硬件应有自己的不小于 256KB 的D-Flash 区域。
HSM 硬件应有自己的不小于１M 的 P-Flash 区域。
P-Flash区域应该被隔离成不同的分区。
整个P-Flash区域应至少划分为一个HSM启动分区和用户软件分区。
HSM启动分区可以OTP 存储区域的形式实现。
HSM硬件需声明支持的硬件加速加解密操作以及数据吞吐量，说明已符合项目需求并取得
安全部门的确认。
HSM硬件需声明支持的硬件加速加签和验签操作以及性能，说明已符合项目需求并取得安
全部门的确认。
如下是某域控提供的性能示例：
HSM硬件应用硬件加速器执行AES128{ECB, CBC, CTR, OFB, GCM, CFB, XTS} 操作。在这
种情况下，数据吞吐量达到至少30MB/s.
HSM硬件应用硬件加速器执行AES256{ECB, CBC, CTR, OFB, GCM, CFB, XTS} 操作。在这
种情况下，数据吞吐量达到至少30MB/s.
HSM 硬件应用硬件加速器执行ECC-256(NIST / Brainpool)曲线，每秒必须完成至少100次验
证和200次签名。
HSM 硬件应用硬件加速器执行ECC Ed25519曲线，每秒必须完成至少100次验证和200次签
名。

5.2 固件需求
5.2.1 通用软件需求
HSM固件用到的RAM空间必须在启动时初始化为定义的值。
5.2.2 加密算法
HSM 固件必须提供满足安全业务需要的加密算法库。
HSM 固件必须使用如在第三章节描述的 HSM 硬件。
如果需要，客户端可以请求额外的加密软件算法，供应商需列举支持的加密算法。
如下是某域控支持的加密算法库描述示例：
HSM 固件支持如 IEEE802.3（以太网标准）指定的 32-bit CRC 校验。
HSM 固件支持按 NIST SP 800-38A 指定的 CBC 模式实施 AES 算法。
HSM 固件必支持按 NIST SP 800-38D 指定的 GCM 模式实施 AES 算法。
会使用 GCM 的 SIV 扩展。
通过 RSA 实验室标准 PKCS # 7: "Cryptographic Message Syntax V1.5"（（在 RFC2315 中描
述））,HSM 固件支持填充。
HSM 固件支持根据PKCS #1 V2.2 支持 RSAES-PKCS1 加密和解密。
HSM 固件支持ECDSA 和 ECIES 算法。
HSM 固件支持 NIST SP 800-38B 和 RFC4493 中指定的MAC 生成和 AES-CMAC 验证。

HSM 固件支持 SipHash24.
5.2.3 安全数据存储
HSM固件必须在HSM内部的非易失性存储器（NVM）中提供安全数据存储区。 NVM存储区域
内的数据块须进行加密和认证。
为了加密和认证NVM区域的数据块，必须使用HSM设备密钥或HSM设备密钥派生的子密钥。
HSM硬件中NVM存储区的损毁情况必须被检测并上报至主机处理器。
供应商需说明数据块的配置以满足项目要求，如下是一个配置示例：
必须能够创建至少20个不同的数据块。
数据块的大小必须是可调整的（1-256字节）。
每一个数据块必须有一个唯一的识别号（16位大小）。
5.2.4 安全密钥存储
HSM固件必须在HSM内部的非易失性存储器（NVM）中提供安全密钥存储区。
每一把存在密钥存储区域的密钥必须是可区分的且可通过数字唯一标识符访问。
加密和认证密码学密钥时，必须使用该存储区专用密钥密钥安全存储必须持有为了此目的预留的
密钥。
推荐使用设备特有的密钥派生此密钥加密和认证密码学密钥。
HSM固件必须保证未加密密钥材料仅存在于HSM安全内存中。
安全密钥区域必须能提供满足业务场景要求的密钥数量存储，并考虑量产后更新密钥的业务员需
求，做出相应预留并取得安全部门同意。
安全密钥区域必须支持最小256bits的对称密钥存储。
安全密钥存储必须支持非对称RSA密钥存储。

5.2.5 RAM-模式

5.2.6 任务处理
HSM固件必须允许任务有不同的优先级别设定。

固件必须支持待处理任务的取消。
固件必须支持正在运行的任务的取消。
5.2.7 基于PSK派生TLS会话密钥
HSM固件必须支持根据PSK派生TLS会话密钥。

5.3.1 HSM升级
HSM 固件的升级必须由 HSM CPU 的控制。这意味着 HSM 固件只能被 HSM 固件自己升级。主
核不能升级 HSM 固件。
在HSM更新过程中，HSM必须能维持可再编程的。

5.3.2 HSM的Autosar集成要求及API定义
HSM的AUTOSAR集成要求，核心是通过间接函数调用扩展CSM功能，同时维持Autosar标准组件
的零修改。
架构关键点图示示意：
AUOSAR CSM模块未提供用于访问所有HSM功能的专用接口。
为了解决这个限制，下面方案建议被使用：
•
间接函数调用
•
元密钥元素
一个定制的HSM功能与CSM函数调用通过专用的CSM作业关联。通过这种方式建立了CSM
函数，CSM作业， HSM功能的密码学原语的唯一映射。
用户程序到HSM定制功能的间接函数调用的转译在HSM的加密驱动中执行。 因此，只有
HSM加密驱动和用户程序需要关注这种间接调用，CSM本身不需关注。
CSM函数和密码学原语与定制HSM实施的实际功能无需存在任何直接关联。
CSM作业匹配至定制的HSM函数调用的确切方式依赖HSM加密驱动的实现。
HSM Crypto驱动的开发者应提供兼容Autosar的机制用于CSM作业匹配至定制的HSM函数
调用。这个机制需要考虑：
•
应用访问HSM函数调用只能通过CSM API。
•
HSM函数调用仅通过要么识别出是CSM API的入参或者识别出CSM API访问特定的密钥元
素的方式接受来自应用的信息。
•
这个信息必须通过一个兼容AUTOSAR标准的机制传递到HSM Crypto 驱动。
•
CSM API的通用功能必须不得受损。
•
不须更改CSM和Crylf来支持该机制。
符合以上要求的机制必须基于专用的CSM作业配置（例如，通过把配置的CSM密钥和HSM
Crypto 驱动内专用特定的密钥映射）。
ECU的集成商应依照要求配置机制，以便CSM作业与正确的HSM函数调用映射，同时用户应
用使用正确的CSM作业。
用户应用可使用不同的方法调用CSM API（如，要么通过AUTOSAR RTE端口或者通过直接
的函数调用）。根据不同的调用方法配置用户应用的方式可不同， 需确保用户应用使用正确
的CSM作业。细节可在各自的应用集成文档中找到。
